# 四层模型

labkit 的全部设计可以归结为一句话：

> **不同层的可信度不同，所以写入权限也必须不同。**

把这句话落实成四个层，是因为最常见的两种失败各来自一个层：

- 把 agent 的自述当作事实 → overclaiming。
- 把当前状态当作历史 → 上下文一断，轨迹消失。

## 分层

```text
意图层   CHARTER / NOTES / CLAIMS / DECISIONS     可错，允许改，允许被推翻
证据层   out= 引用的产物、数据、配置、哈希          可核对，指向不可变的东西
审计层   git 历史、文件内容                        不可由 agent 撰写
交接层   STATE / LOG / archive                     易过期，靠上限保持可用
```

### 意图层

**是什么**：这个项目想回答什么、相信什么、打算怎么做、决定了什么。

**谁写**：agent 和人都可以，且允许写错。

**为什么允许错**：研究本来就是从错假设里往前走的。要求意图层永远正确，只会让人不敢写。

**如何控制风险**：不靠"写对"，靠"可推翻"。每条假设必须带推翻条件；
每条断言创建时必须带判据；每个决定必须写代价。

### 证据层

**是什么**：对产物的引用，不是产物本身。

```text
out=runs/natural_384/results.csv
out=human/sINR_base/log/natural_layer_ablation_4images_20k_20261024
commit=4b9c1e2
sha256=f0dbc896...
```

**谁写**：任何人，但**路径必须真实**。

**关键纪律**：证据层只引用，不复制。数字放在 `results.csv`，
RUNS 只写"结果在哪"。复制会分叉，分叉后没人知道哪份是对的。

**为什么可信度高于意图层**：产物是训练脚本跑出来的，可以被重新检查。
"我认为结果很好"不能。

### 审计层

**是什么**：git 历史、文件内容本身。

**谁写**：**没人手动写**。它由 git 在提交时生成。

**为什么单独一层**：这是整份规范里唯一"agent 无法伪造"的部分。
一个由 agent 自己写的记录，无法用来核查 agent 的结论——它的结论和记录来自同一个可能出错的来源。

**labkit 的做法**：不实现审计，只**依赖**它。所以：

- 不提供"记录我改了什么"的命令，那会制造一层伪审计。
- 要求有意义的检查点提交，commit message 写为什么。
- 不改写已共享的历史。
- 需要追溯某个数字时，去看那次 commit 对应的脚本与配置快照。

### 交接层

**是什么**：现在在哪、刚刚发生了什么。

**谁写**：接手的 agent。

**为什么需要独立一层**：它是唯一**会过期**的一层。意图层和证据层长期有效，
交接层一周不看就不准了。过期的东西必须能整份替换，所以 STATE 是覆盖式。

**如何保持可用**：靠上限。STATE ≤60 行、LOG ≤40 条。长了的交接层没人读，
没人读的交接层等于不存在。

## 层间关系

```text
CHARTER ──决定──> DESIGN ──产生──> RUNS ──引用──> 产物
   │                  │                              │
   │                  └──检验──> CLAIMS <──证据──────┘
   │                                │
   └──────约束──────────────────────┘
                                    │
                              BASE（结算后的事实）
                                    │
                    git ──审计全部──> commit 历史
```

要点：

1. **CHARTER 只向下约束**，不被结果改写。问题变了，是换项目，不是改章程。
2. **CLAIMS 是 RUNS 与结论之间的桥**。没有它，RUNS 只是一堆数字，BASE 里的事实无从追。
3. **BASE 是漏斗底**。只有结算过的事实才进 BASE，未验证的留在 THINKING。
4. **git 横向审计所有层**，但它只在提交点存在——不提交等于没有审计。

## 一个常见的错误切法

把"笔记"和"日志"当成两层。它们其实是同一层（意图层 + 交接层）的不同写入频率：

- 笔记 = 低频、结构化、长期
- 日志 = 高频、一行、短期

分开存放是对的，但**不要以为日志能代替笔记**。日志记录"做了什么"，
笔记记录"为什么"。三个月后你需要的几乎总是后者。

## 另一个常见错误

把"证据"和"结论"混在一起写：

```text
✗ 24L 比 12L 好 1.8 dB（见 results.csv）
```

这句话同时包含结论和证据，看起来高效，实际上：

- 结论没有标状态，无法区分已确立和初步；
- 证据只给了文件名，没给筛选条件，无法核对是哪几行；
- 结论被推翻时，只能整句删掉，丢失历史。

正确的拆法是两份记录：`CLAIMS/C00x.md` 记结论和判据，
`RUNS.md` / 产物记证据。两者用编号互指。

## 何时不需要四层

| 情况 | 建议 |
|---|---|
| 一次性脚本、玩两小时 | 不要用 labkit，直接写 README |
| 单人、单一 agent、两周内结束 | 只需要 CHARTER + STATE |
| 需要对外交付 | 加上 CLAIMS 和 BASE，交付物必须可追溯 |
| 多人多 agent、数月以上 | 全部档位，且严格遵守上限 |
