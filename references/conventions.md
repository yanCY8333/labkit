# 写作规则

这些规则的存在理由是**可读性衰减**。一个文件第一次写总是好读的，
三个月后还能读，靠的是当时就遵守了上限和结构。

## 有界

| 文件 | 上限 | 超了怎么办 |
|---|---|---|
| `STATE.md` | 60 行 | 删掉已过期的内容（历史在 LOG） |
| `LOG.md` | 40 条 | 最旧的移入 `archive/` |
| `CHARTER.md` | 40 行 | 说明范围失控，回去砍问题 |
| `NOTES/BASE.md` | 80 行 | 合并同类项，细节下沉到 CLAIMS / RUNS |
| `DECISIONS.md` 单条 | 6 行 | 拆成两个决定，或写进 NOTES |
| `NOTES/THINKING.md` 单条 | 25 行 | 细节进 DESIGN |
| `NOTES/DESIGN.md` 单个设计 | 80 行 | 协议下沉到 `NOTES/PROTOCOL.md` |
| `NOTES/RUNS.md` 单条 | 15 行 | 数字放产物文件，这里只留指针 |
| `CLAIMS/Cxxx.md` | 60 行 | 断言太大，拆成两条 |

**上限不是建议。** 超限是信号：要么内容没整理，要么这个文件承担了它不该承担的职责。

## 长文档先写 TL;DR

超过 40 行的文件，顶部必须有 5 行以内的摘要：

```markdown
> TL;DR：24 层金字塔在 full 上稳定优于 12 层约 1.8 dB；
>        sparse 上排序反转，宽骨干最优容量是 6 层。
>        待验证：纯细尺度对照（C003）。
```

没有 TL;DR 的长文档，等于假设读者会读完。他们不会。

## 编号

| 前缀 | 用于 | 示例 |
|---|---|---|
| `C` | 断言（claim） | `C007` |
| `D` | 决定（decision） | `D012` |
| `R` | 运行（run） | `R031` |
| `Q` | 子问题（charter 拆解） | `Q003` |

- 编号**只增不复用**。删掉一条记录，它的编号也随之作废，不再分配给新条目。
- 编号在 `INDEX.md` 或文件内出现一次即可，不要到处复制正文。

## 链接

三种引用方式，只用这三种：

| 写法 | 含义 |
|---|---|
| `[[C007]]` | 指向断言 |
| `see D012` | 指向决定 |
| `out=path/to/artifact` | 指向证据（**必须是真实路径**） |

不要用相对链接指向其他 markdown 的锚点——重命名一次就全断。用编号。

## 追加 vs 覆盖 vs 划掉

| 动作 | 用在哪 | 规则 |
|---|---|---|
| **追加** | LOG、DECISIONS、RUNS、THINKING 新条目 | 只在末尾加 |
| **覆盖** | STATE | 整份重写，短就是目的 |
| **划掉** | BASE 里被推翻的事实、CLAIMS 里被修改的结论 | 保留原文 + 标记 + 指向新结论 |

划掉的写法：

```text
- ~~✅ 24L 总是优于 12L~~ → 已被 C009 推翻：sparse 上 12x20 反转
```

**禁止静默删除已结算的结论。** 结论变化本身是信息；抹掉它等于伪造历史。

## 状态词

固定八个，不要自创同义词：

| 词 | 含义 | 用在哪 |
|---|---|---|
| `open` | 还没开始验证 | CLAIMS、THINKING |
| `testing` | 正在验证 | CLAIMS |
| `met` | 判据满足 | CLAIMS |
| `not_met` | 判据不满足 | CLAIMS |
| `inconclusive` | 样本不足或结果矛盾 | CLAIMS |
| `dropped` | 主动放弃，附理由 | CLAIMS、THINKING |
| `✅ ◐ ❌ ❓` | 已确立 / 初步 / 已排除 / 未验证 | BASE |
| `生效 / 被取代` | 决定是否仍然有效 | DECISIONS |

`met` / `not_met` 是**记录**，不是**裁决**。labkit 不验证它是否正确；
验证发生在证据层（产物文件）和审计层（git）。写下 `met` 的人要为它负责。

## LOG 的写法

```text
时间 | agent | 类型 | 一句话  out=产物路径
```

- 时间：`YYYY-MM-DD HH:MM`，本地时间。
- agent：`模型/客户端`，如 `claude/opus`、`deepseek/flash`、`human`。
- 一句话：≤240 字，写**动作和结果**，不写过程。
- `out=`：产物路径或目录，可省略（纯决策类动作没有产物）。

判断标准：**三个月后的人，能不能靠这一行定位到东西或还原当时状态**。不能就不记。

## 什么不该记

| 不要记 | 原因 | 该去哪 |
|---|---|---|
| 读文件、列目录、搜索 | 噪音，淹没真正的动作 | 不记 |
| 思考草稿、犹豫、反复确认 | 不是状态变化 | THINKING（且只记结论） |
| 同一个动作拆成多条 | 日志膨胀的主因 | 合成一条 |
| 完整的数据表、长代码 | LOG 会变成仓库 | 产物文件 + 指针 |
| "我改了什么"当作审计 | agent 自述不可信 | git |
| 已经写进 BASE 的完整结论 | 重复 | LOG 一条指针即可 |

## git 的使用

labkit 不实现审计，**依赖 git**：

- 每个有意义的检查点提交一次，commit message 写"为什么"。
- 大产物用 `.gitignore` 排除，但**提交生成它的脚本和配置**。
- 需要证明"某个结果出自某次运行"，靠 commit SHA + 产物内的配置快照。
- 不要用 force push 或 amend 改写已共享的历史——那会销毁审计层。

## 字数与语言

- 中文为主，路径、字段名、状态词用英文。
- 专有名词首次出现给全称，之后用缩写。
- 不用"显然"、"众所周知"——它们标记的是作者没想清楚的地方。
